# Introduction

`SearchService`, `ExploreService`, and `LibraryService` in `src/gui/services/` currently
execute all SQLite queries synchronously on the GUI thread. On slow hardware or against a
large database this stalls `QApplication::exec()`, producing visible UI freezes whenever
a screen is loaded or the user types in the search bar.

This spec defines a `QueryWorker` background thread that owns its own SQL connection and
runs all read queries (and write operations that do not need an immediate return value)
off the GUI thread. Results are delivered back to the GUI thread via Qt signals so that
screens update reactively without blocking the event loop.

## 1. Purpose & Scope

Covers:

1. A new `QueryWorker : QObject` class moved onto a `QThread`, owning the
   `"gui_query_connection"` SQL connection.
2. Signal-based async API replacements for every public method on `SearchService`,
   `ExploreService`, and the read path of `LibraryService`.
3. Special handling for `LibraryService` write methods that currently return a value
   (`addBook`) or a success flag (`removeBook`, `updateStatus`).
4. Screen-side wiring changes for `SearchScreen`, `LibraryScreen`, and `ExploreScreen`.
5. Connection lifecycle management relative to `QApplication` startup and shutdown.
6. An adaptation strategy for the ten existing tests that rely on the synchronous API.
7. A migration path that minimises code churn while keeping the synchronous query logic
   intact as an implementation detail.

Out of scope: full-text search indexing, SQLite WAL mode configuration, write-ahead
coalescing, download flow, audiobook conversion, and any UI not yet implemented
(Book Details screen, Task 9 and above).

## 2. Definitions

| Term | Meaning |
|------|---------|
| GUI thread | The OS thread that runs `QApplication::exec()` and owns all `QWidget` instances |
| Collector thread | `CollectorWorker : QThread` — polls Gutenberg metadata; owns `"collector_connection"` |
| Query thread | New `QThread` introduced by this spec; owns `"gui_query_connection"` |
| `QueryWorker` | `QObject` subclass moved onto the query thread; executes SQL and emits result signals |
| Request signal | Qt signal fired from the GUI thread to the `QueryWorker` via `Qt::QueuedConnection`; carries query parameters |
| Result signal | Qt signal fired back from the `QueryWorker` to the GUI thread (also queued); carries the result data |
| `requestId` | A `quint64` monotonically incrementing token generated by the service on the GUI thread. Used by screens to discard stale responses when a new request supersedes an in-flight one |
| Synchronous path | The existing service methods (`search(...)`, `fetchItems(...)`, etc.) that call `QSqlDatabase::database()` — retained as private helpers called from within `QueryWorker` |
| `Qt::QueuedConnection` | Qt cross-thread signal delivery mode; the slot executes in the receiver's thread |

## 3. Requirements, Constraints & Guidelines

### Requirements

- **REQ-001**: All read queries (`SearchService::search`, `SearchService::count`,
  `SearchService::fetchDistinctLanguages`, `SearchService::fetchDistinctSources`,
  `SearchService::fetchGenres`, `ExploreService::fetchTrending`,
  `ExploreService::fetchNewArrivals`, `ExploreService::fetchCategories`,
  `ExploreService::fetchBooksForGenre`, `LibraryService::fetchItems`) must execute on
  the query thread, not the GUI thread.

- **REQ-002**: Write operations on `LibraryService` (`addBook`, `removeBook`,
  `updateStatus`) must also execute on the query thread.

- **REQ-003**: Result signals must be delivered to the GUI thread. All widget mutations
  must happen in a slot connected to a result signal, not inside `QueryWorker`.

- **REQ-004**: Each async request must carry a `requestId` so that screens can detect
  and silently discard responses that arrive after a newer request has already been
  submitted (stale response suppression).

- **REQ-005**: `LibraryService::addBook` currently returns the new `library_items.id`.
  The async replacement must deliver this value via a dedicated result signal rather
  than a return value.

- **REQ-006**: Write operation result signals must include a success/failure boolean and,
  for `addBook`, the new row ID. The existing `libraryChanged` signal must still be
  emitted on the GUI thread after any successful write so that `LibraryScreen::reload()`
  continues to function without changes to its connection logic.

- **REQ-007**: `LibraryScreen` must display a loading indicator (the existing index-2
  stack page with the `QProgressBar`) while the initial `fetchItems` request is in
  flight. It must already has this state wired — the spec simply requires that the
  transition away from it happens in the `fetchItemsCompleted` slot rather than
  synchronously at the end of `init()`.

- **REQ-008**: `SearchScreen` must disable the search bar or show a visual busy
  indicator while a `search` or `count` request is in flight, to prevent stacking
  duplicate requests from fast typists. Disabling the "Load more" button while an
  `onLoadMore` request is in flight is sufficient; the debounce timers already handle
  the main search bar.

- **REQ-009**: The query thread and its SQL connection must be created before any screen
  is constructed and must be cleanly shut down after all screens are destroyed but
  before `QSqlDatabase::removeDatabase` is called.

- **REQ-010**: No `QProcess` may be used anywhere in the implementation. No new GPL
  dependencies may be introduced.

- **REQ-011**: `Qt6::Concurrent` must NOT be linked. The `QThread`-based
  `QueryWorker` approach must be used (see Section 6 for rationale).

- **REQ-012**: All new code must reside under the `bookhub::gui` namespace and follow
  the project's `camelCase` member naming convention with the `m_` prefix.

- **REQ-013**: `tests/support/test_database_utils.h` — `TestDatabase` must expose a
  `filePath() const` accessor returning the path of the temporary database file. This
  allows a second `QSqlDatabase` connection (opened by `TestQueryWorker`) to be pointed
  at the same file. No change to the existing `open()` signature is required; the path
  is derived from the existing `QTemporaryDir`.

### Constraints

- **CON-001**: Each thread must use its own named `QSqlDatabase` connection. The GUI
  thread retains `QSqlDatabase::defaultConnection`. The collector thread retains
  `"collector_connection"`. The query thread uses `"gui_query_connection"`.
  A single `QSqlDatabase` connection object must never be shared across threads.

- **CON-002**: `QueryWorker` must be constructed on the GUI thread and moved to the
  query thread via `QObject::moveToThread()` before the thread is started. Its
  SQL connection must be opened inside a slot connected to `QThread::started`.

- **CON-003**: The SQL connection owned by `QueryWorker` must be closed and removed
  (`QSqlDatabase::removeDatabase`) inside a slot connected to `QThread::finished`
  to ensure the connection is released from the thread that owns it.

- **CON-004**: `QueryWorker` must not hold a `QSqlDatabase` value member directly —
  it must call `QSqlDatabase::database("gui_query_connection")` at query time, as
  Qt SQL connections are thread-local.

- **CON-005**: The three service classes (`SearchService`, `ExploreService`,
  `LibraryService`) remain `QObject` subclasses living on the GUI thread. They become
  thin facades: they generate a `requestId`, emit a request signal to `QueryWorker`,
  and re-emit the result signal received from `QueryWorker` to their own callers.

- **CON-006**: The existing synchronous query implementations (the private static
  helpers `buildSql`, `bindParams`, `execBookQuery`, and all `fetchItems`/`addBook`/
  etc. method bodies) must be refactored into free functions or private static methods
  that `QueryWorker` calls. They must NOT be removed or duplicated.

- **CON-007**: `ExploreScreen::buildTopLevelPage()` currently calls service methods
  directly in the constructor path. After this change it must instead trigger async
  requests and use placeholder (empty) data to build the initial widget tree,
  populating carousels and the category grid lazily when results arrive.

### Guidelines

- **GUD-001**: `requestId` values should be generated by an `std::atomic<quint64>`
  counter in each service (or a single shared counter in `QueryWorker`). Using a
  counter rather than a random UUID keeps the implementation simple and deterministic
  in tests.

- **GUD-002**: Services should expose a `bool isBusy() const` method that returns true
  while any request is in flight (i.e., a request has been emitted but the result
  signal has not yet been received). This simplifies loading-state logic in screens.

- **GUD-003**: Stale response suppression in screens should be implemented by storing
  the `requestId` of the most recently submitted request and comparing it in the
  result slot. A helper `bool isCurrentRequest(quint64 id) const` avoids repeating
  this pattern in multiple screens.

- **GUD-004**: The `LibraryService` `libraryChanged` signal should be emitted from
  within the write result slots on the GUI thread (after verifying success), not from
  inside `QueryWorker`. This preserves all existing connections without modification.

- **GUD-005**: Prefer direct function calls from `QueryWorker` into the refactored
  query helpers rather than re-introducing a dependency on the service class objects.
  `QueryWorker` should own the SQL logic; services should own the API surface.

## 4. Interfaces & Data Contracts

### 4.1 New file: `src/gui/query_worker.h`

```cpp
namespace bookhub::gui {

// ---------------------------------------------------------------------------
// QueryWorker — executes SQL on the dedicated query thread.
//
// Lifetime: constructed on the GUI thread, moved to m_queryThread via
// moveToThread(), then started. The SQL connection is opened in onThreadStarted
// and closed in onThreadFinished.
//
// All request signals are connected Qt::QueuedConnection from the service
// objects (GUI thread) to this worker (query thread).
// All result signals are emitted from this worker and received Qt::QueuedConnection
// by the service objects on the GUI thread.
// ---------------------------------------------------------------------------

class QueryWorker : public QObject {
    Q_OBJECT
public:
    explicit QueryWorker(QObject *parent = nullptr);

public slots:
    void onThreadStarted();   // opens "gui_query_connection"
    void onThreadFinished();  // closes and removes "gui_query_connection"

    // --- SearchService requests ---
    void handleSearchRequest(quint64 requestId, const bookhub::gui::SearchParams &params,
                             int offset, int limit);
    void handleCountRequest(quint64 requestId, const bookhub::gui::SearchParams &params);
    void handleLanguagesRequest(quint64 requestId);
    void handleSourcesRequest(quint64 requestId);
    void handleGenresRequest(quint64 requestId);

    // --- ExploreService requests ---
    void handleTrendingRequest(quint64 requestId);
    void handleNewArrivalsRequest(quint64 requestId);
    void handleCategoriesRequest(quint64 requestId);
    void handleBooksForGenreRequest(quint64 requestId,
                                    const QString &genre,
                                    int offset, int limit);

    // --- LibraryService requests ---
    void handleFetchItemsRequest(quint64 requestId, const QString &sortColumn);
    void handleAddBookRequest(quint64 requestId,
                              const QString &bookId, int editionId);
    void handleRemoveBookRequest(quint64 requestId, int libraryItemId);
    void handleUpdateStatusRequest(quint64 requestId,
                                   int libraryItemId, const QString &status);

signals:
    // --- SearchService results ---
    void searchCompleted(quint64 requestId, QList<bookhub::gui::SearchResult> results);
    void countCompleted(quint64 requestId, int count);
    void fetchLanguagesCompleted(quint64 requestId, QStringList languages);
    void fetchSourcesCompleted(quint64 requestId, QStringList sources);
    void fetchGenresCompleted(quint64 requestId, QStringList genres);

    // --- ExploreService results ---
    void fetchTrendingCompleted(quint64 requestId, QList<bookhub::gui::ExploreBook> books);
    void fetchNewArrivalsCompleted(quint64 requestId, QList<bookhub::gui::ExploreBook> books);
    void fetchCategoriesCompleted(quint64 requestId, QList<bookhub::gui::ExploreCategory> categories);
    void fetchBooksForGenreCompleted(quint64 requestId, QList<bookhub::gui::ExploreBook> books);

    // --- LibraryService results ---
    void fetchItemsCompleted(quint64 requestId, QList<bookhub::gui::LibraryItem> items);
    // bookId is echoed back to avoid a QHash<quint64,QString> lookup in the caller.
    // newId is the library_items.id on success, -1 on failure or duplicate.
    void addBookCompleted(quint64 requestId, QString bookId, bool success, int newId);
    void removeBookCompleted(quint64 requestId, bool success);
    void updateStatusCompleted(quint64 requestId, bool success);
};

} // namespace bookhub::gui
```

### 4.2 Updated `SearchService` public API (`src/gui/services/search_service.h`)

The synchronous methods are removed from the public interface and become private helpers
called by `QueryWorker`. The new public API is signal-based:

```cpp
class SearchService : public QObject {
    Q_OBJECT
public:
    explicit SearchService(QObject *parent = nullptr);

    // Async request methods — return the requestId assigned to this request.
    // The caller stores this id and compares it in the result slot.
    quint64 requestSearch(const SearchParams &params, int offset = 0, int limit = 50);
    quint64 requestCount(const SearchParams &params);
    quint64 requestLanguages();
    quint64 requestSources();
    quint64 requestGenres();

    bool isBusy() const;

signals:
    // Emitted when the query thread delivers results for requestSearch()
    void searchCompleted(quint64 requestId, QList<SearchResult> results);
    // Emitted when the query thread delivers results for requestCount()
    void countCompleted(quint64 requestId, int count);
    void languagesCompleted(quint64 requestId, QStringList languages);
    void sourcesCompleted(quint64 requestId, QStringList sources);
    void genresCompleted(quint64 requestId, QStringList genres);

    // --- Internal request signals (connected Qt::QueuedConnection to QueryWorker) ---
    // These are technically public (Qt signals are always public) but are
    // documented as internal — callers must use the request*() methods, not
    // emit these directly.
    void searchRequested(quint64 requestId, SearchParams params, int offset, int limit);
    void countRequested(quint64 requestId, SearchParams params);
    void languagesRequested(quint64 requestId);
    void sourcesRequested(quint64 requestId);
    void genresRequested(quint64 requestId);
};
```

### 4.5 `QueryWorker` ownership and wiring in `MainWindow`

`MainWindow` creates the `QueryWorker` and its `QThread` before constructing any screen.
The services are also created here (or passed into screens as today) and are wired to the
worker at construction time:

```cpp
// In MainWindow constructor, before any screen is created:

m_queryThread = new QThread(this);
m_queryWorker = new QueryWorker;          // no parent — will be moved to thread
m_queryWorker->moveToThread(m_queryThread);

connect(m_queryThread, &QThread::started,
        m_queryWorker, &QueryWorker::onThreadStarted);
connect(m_queryThread, &QThread::finished,
        m_queryWorker, &QueryWorker::onThreadFinished);
connect(m_queryThread, &QThread::finished,
        m_queryWorker, &QObject::deleteLater);

m_libraryService = new LibraryService(this);
m_libraryService->connectToWorker(m_queryWorker);   // see §4.6

m_queryThread->start();

// Then construct screens as before, passing m_libraryService where needed.
```

`SearchScreen` and `ExploreScreen` construct their own service instances in their
constructors (current behaviour). Those service instances must also be wired to the
shared `QueryWorker`. The cleanest approach is for `MainWindow` to pass the
`QueryWorker*` to each screen constructor, which calls `service->connectToWorker(worker)`
internally.

Alternative: expose a `MainWindow::queryWorker()` accessor and have screens call it
from `QApplication::instance()`. The first approach (explicit injection) is preferred
because it avoids a global dependency and makes the connection visible at the call site.

### 4.6 `connectToWorker()` pattern

Each service exposes:

```cpp
// Called once after the QueryWorker has been moved to its thread but before
// any request method is called. Establishes all QueuedConnection wires.
void connectToWorker(QueryWorker *worker);
```

Inside `connectToWorker`, the service connects:
- Its internal `*Requested` signals to the worker's `handle*Request` slots
  (`Qt::QueuedConnection`)
- The worker's `*Completed` signals to the service's own `*Completed` signals
  (`Qt::QueuedConnection`)

The service re-emits the worker's results as its own signals so that screens connect
to the service (not directly to the worker), preserving encapsulation and making test
substitution straightforward.

### 4.7 Shutdown sequence in `MainWindow` destructor

```
1. m_queryThread->quit()            // posts QEvent::Quit to the query thread's event loop
2. m_queryThread->wait(3000)        // give the thread up to 3 s to finish its current query
3. // QThread::finished fires → onThreadFinished closes "gui_query_connection"
4. // QObject::deleteLater cleans up m_queryWorker
5. MainWindow destructor completes, then QApplication destroys defaultConnection
```

Step 2 uses a timeout guard. If the thread does not finish within 3 seconds (pathological
long query), terminate it and log a warning. This avoids a hang on application exit.

### 4.8 Screen changes — `SearchScreen`

`SearchScreen::runSearch()` currently calls `m_service->count()` and `m_service->search()`
synchronously and populates the model inline. The new flow:

1. `runSearch()` calls `m_service->requestCount(params)` and stores the returned
   `requestId` as `m_pendingCountId`. It also disables the `m_loadMoreBtn`.
2. `onCountCompleted(quint64 id, int count)` slot: if `id == m_pendingCountId`, stores
   `m_totalCount`, updates the count label, then calls `m_service->requestSearch(params,
   0, kPageSize)`, storing the returned id as `m_pendingSearchId`. Discards if stale.
3. `onSearchCompleted(quint64 id, QList<SearchResult> results)` slot: if `id ==
   m_pendingSearchId`, calls `populateModel(results, false)` and updates the
   `m_resultsStack` and `m_loadMoreBtn` visibility. Discards if stale.

`onLoadMore()` similarly calls `requestSearch` with the current offset and stores
`m_pendingLoadMoreId`. Its completion slot appends to the model.

`SearchScreen::SearchScreen()` still calls `requestLanguages()`, `requestSources()`,
and `requestGenres()` at construction time. The filter lists are populated lazily in
the corresponding `*Completed` slots rather than immediately. The constructor must not
block on these results.

### 4.9 Screen changes — `LibraryScreen`

`LibraryScreen::reload()` currently calls `m_service->fetchItems(col)` synchronously.
The new flow:

1. `reload()` sets `m_stack->setCurrentIndex(2)` (loading state) and calls
   `m_service->requestFetchItems(col)`, storing the returned id as `m_pendingFetchId`.
2. `onFetchItemsCompleted(quint64 id, QList<LibraryItem> items)` slot: if `id ==
   m_pendingFetchId`, calls `populateModel(items)`, `updateCountLabel(items.size())`,
   and `m_stack->setCurrentIndex(items.isEmpty() ? 1 : 0)`.

`onRemoveRequested` currently calls `m_service->removeBook(id)` synchronously and the
`libraryChanged` signal triggers `reload()`. The new flow:
1. `onRemoveRequested` confirms the dialog, then calls `m_service->requestRemoveBook(id)`.
2. `LibraryService` emits `libraryChanged` from the `removeBookCompleted` slot after
   confirming `success == true`.
3. `LibraryScreen::reload()` is triggered as before through `libraryChanged`.

### 4.10 Screen changes — `ExploreScreen`

`ExploreScreen::buildTopLevelPage()` is currently called from the constructor and calls
service methods synchronously to populate the carousels and category grid. This must
change because service methods are now async.

The new approach separates widget construction from data population:

1. `buildTopLevelPage()` creates the carousels and category grid with empty data
   (showing placeholder labels).
2. A new `loadTopLevelData()` method (called from the constructor after widget setup)
   calls `m_service->requestTrending()`, `requestCategories()`, and
   `requestNewArrivals()`, storing the three request IDs.
3. Completion slots (`onTrendingCompleted`, `onCategoriesCompleted`,
   `onNewArrivalsCompleted`) replace the carousel/grid contents when data arrives.
   Each slot calls a helper that clears the existing carousel/grid widgets and
   repopulates them with the received data.

`appendGenreBooks()` currently calls `m_service->fetchBooksForGenre()` synchronously.
The new flow:
1. `appendGenreBooks(offset)` calls `m_service->requestBooksForGenre(...)`, stores the
   returned id as `m_pendingGenreId`, and disables `m_loadMoreBtn` while in flight.
2. `onBooksForGenreCompleted(quint64 id, QList<ExploreBook> books)` slot: if `id ==
   m_pendingGenreId`, appends cards to the grid and updates `m_loadMoreBtn` visibility.

### 4.11 `SearchScreen` constructor — `LibraryService` write path

`SearchScreen::onAddToLibrary` currently calls `m_libraryService->addBook(bookId, 0)`
synchronously and uses the returned `newId` only to check for failure (`newId < 0`). It
does not store the ID. The new flow:

1. `onAddToLibrary` calls `m_libraryService->requestAddBook(bookId, 0)`.
2. `onAddBookCompleted(quint64 id, QString bookId, bool success, int /*newId*/)` slot:
   uses the `bookId` carried directly in the signal to locate the model row, and if
   `success`, flips the `InLibrary` flag as before. No `QHash` lookup is required
   because `bookId` is echoed back through the signal chain from `QueryWorker`.

### 4.12 `requestId` counter

Each service owns one `std::atomic<quint64> m_nextRequestId{1}` member. The
`request*()` methods increment and return `m_nextRequestId.fetch_add(1,
std::memory_order_relaxed)` before emitting the request signal. ID 0 is reserved as
"no pending request" so screens can initialise their pending-ID trackers to 0.

### 4.13 CMakeLists.txt changes

Add `Qt6::Concurrent` to `find_package` and `target_link_libraries` only if
`QtConcurrent` is used elsewhere; per REQ-011 it must not be linked for this feature.
No CMake changes are required for the `QThread`-based approach.

Add `src/gui/query_worker.cpp` to `GUI_SOURCES` in `CMakeLists.txt`.

## 5. Acceptance Criteria

- **AC-001**: Given the application is launched on hardware where a full-table scan of
  `books` takes more than 100 ms, When the Search tab is opened and the user types a
  keyword, Then the UI remains responsive (no visible freeze) while the query is
  executing on the query thread.

- **AC-002**: Given a `SearchScreen` is shown and a search is in progress, When the
  user types a second query before the first completes, Then only the results for the
  most recent query are applied to the model (stale results are silently discarded).

- **AC-003**: Given `LibraryScreen` is constructed with sample data in the database,
  When the constructor calls `reload()`, Then the screen briefly shows index 2 (loading

  or index 1 (empty state) as appropriate.

- **AC-004**: Given `SearchScreen::onAddToLibrary` is called, When the `addBook` write
  completes successfully on the query thread, Then the `InLibrary` flag on the affected
  model row is flipped to `true` and `libraryChanged` is emitted on the GUI thread.

- **AC-005**: Given the application is shut down while a query is in flight, When
  `MainWindow` is destroyed, Then the query thread is stopped cleanly within 3 seconds,
  the `"gui_query_connection"` connection is removed, and no QSqlDatabase teardown
  warnings are logged.

- **AC-006**: Given `ExploreScreen` is constructed with categories in the database, When
  the constructor completes, Then the category grid is initially empty (or shows a
  placeholder) and is populated asynchronously when `categoriesCompleted` fires.

- **AC-007**: Given a `LibraryService` write (`removeBook`) is initiated from a dialog
  confirmation, When the operation completes successfully on the query thread, Then
  `libraryChanged` is emitted on the GUI thread and `LibraryScreen::reload()` triggers
  a new async `fetchItems` request.

- **AC-008**: Given all three integration test targets (`test_search_service`,
  `test_library_service`, `test_explore_service`) are run, When `ctest` executes them,
  Then all pass. The integration tests exercise the synchronous query helpers directly
  (see Section 8) and do not require a live query thread.

- **AC-009**: Given all three GUI screen test targets (`test_search_screen`,
  `test_library_screen`, `test_explore_screen`) are run, When `ctest` executes them
  using a synchronous `TestQueryWorker` that executes all slots in-process without
  starting a real thread, and `QSignalSpy` on result signals for assertions, Then all
  pass.

- **AC-010**: Given the full `ctest` suite is run, When it completes, Then all 10
  targets pass and no SQL connection teardown warnings appear in the test output.

## 6. Rationale & Context

### 6.1 Architecture choice: `QThread`-based `QueryWorker` vs `QtConcurrent::run()`

Both approaches move SQL execution off the GUI thread, but they differ significantly
in lifecycle management and connection ownership:

| Criterion | `QThread` + `QueryWorker` | `QtConcurrent::run()` |
|-----------|--------------------------|----------------------|
| SQL connection ownership | Single connection per thread; opened once, closed on `finished` | One connection per `QThreadPool` worker; connections multiply and cannot be reliably closed |
| Thread count | 1 dedicated query thread | Up to `QThread::idealThreadCount()` pool threads |
| Result delivery | Native Qt signals | `QFutureWatcher` or manual `invokeMethod` |
| `Qt6::Concurrent` dependency | Not required | Required (REQ-011 forbids this) |
| Test substitution | Straightforward — swap the connection and skip the thread | Requires custom executors or test-thread management |
| Shutdown guarantee | `QThread::quit()` + `wait()` gives a deterministic teardown window | No per-request cancellation; `QThreadPool::waitForDone` blocks indefinitely on slow queries |

**Decision:** Use `QThread` + `QueryWorker`. The single-connection model maps directly
onto SQLite's thread-isolation requirement. The `Qt::QueuedConnection` signal path
integrates naturally with the existing signal/slot architecture throughout the
codebase. `QtConcurrent` is explicitly forbidden by REQ-011 both because it is not
currently linked and because it does not provide a clean single-connection lifecycle.

**WAL mode context:** `database.cpp` already enables `PRAGMA journal_mode = WAL`. This
means the query thread can read concurrently while the collector thread holds a write
lock, providing genuine three-way parallelism (GUI event loop, query reads, collector
writes) rather than merely moving blocking off the GUI thread.

### 6.2 Synchronous helpers as `QueryWorker` internals

The existing `SearchService`, `LibraryService`, and `ExploreService` implementations
contain well-tested SQL construction logic (`buildSql`, `bindParams`, `execBookQuery`,
whitelist-guarded `ORDER BY` builders). Discarding and rewriting this logic would
introduce regression risk and duplicate effort. Instead, the implementation extracts
these helpers into free functions in a shared translation unit (or as private static
methods on `QueryWorker`) that is callable from both the worker (production path)
and directly from tests (test path, bypassing the thread). This is the
lowest-disruption migration path.

### 6.3 `libraryChanged` signal routing

`LibraryScreen` is connected to `LibraryService::libraryChanged` at construction time.
`SearchScreen::onAddToLibrary` also indirectly relies on the library refresh mechanism.
Keeping `libraryChanged` emitted from the GUI thread (inside `LibraryService`'s result
slots) means zero changes to these connection sites. Emitting it from inside
`QueryWorker` would require a queued connection and would force all downstream slots to
handle both queued and direct delivery, increasing the risk of double-refresh races.

### 6.4 `ExploreScreen` constructor redesign

The current `ExploreScreen` constructor calls `buildTopLevelPage()` which calls service
methods immediately, making widget construction and data loading a single synchronous
step. Separating these into `buildTopLevelPage()` (pure widget construction) and
`loadTopLevelData()` (async requests) aligns with how `LibraryScreen` already handles
the distinction between construction and the `reload()` call.

### 6.5 `addBook` return value

`addBook` returns the new `library_items.id`. Examining all call sites:
- `LibraryService::addBook` in `search_screen.cpp` checks only `newId < 0` for failure;
  the actual ID value is not stored or used.
- `test_library_service.cpp` uses the returned ID to subsequently call `updateStatus`
  and `removeBook` on the same row.

The production call site therefore requires only a `success` boolean. The test (Section
8) is the only consumer of the actual ID, and tests will use the synchronous helper
path directly, so the async `addBookCompleted(requestId, success, newId)` signal
carries the ID to satisfy future callers at no cost.

## 8. Test Strategy

### 8.1 Integration tests — synchronous query helpers

`test_search_service`, `test_library_service`, and `test_explore_service` currently
construct service objects and call synchronous methods against a `defaultConnection`
test database. After this change the synchronous methods are no longer part of the
public API; they become private helpers called from within `QueryWorker`.

**Adaptation:** Extract the query logic into free functions in a new
`src/gui/query_helpers.h/.cpp` (or into `QueryWorker` private static methods) and expose
a narrow internal-test header (`src/gui/query_worker_testable.h`, included only by
`#ifdef BOOKHUB_TESTING`) that allows the integration tests to call the helpers directly,
bypassing the thread. The `TestDatabase` helper already opens the `defaultConnection`; the
helpers must accept a connection name parameter so they can be called against any named
connection.

Example adapted test pattern:

```cpp
// Old:
SearchService service;
const QList<SearchResult> results = service.search(params);

// New (calls the extracted helper directly on the test connection):
const QList<SearchResult> results =
    bookhub::gui::internal::runSearch(params, 0, 50,
                                      QSqlDatabase::defaultConnection);
```

All existing assertions remain unchanged — only the call site changes.

### 8.2 GUI screen tests — async flow with event loop draining

`test_library_screen`, `test_search_screen`, and `test_explore_screen` currently
call service methods and expect synchronous model mutations. After this change the model
is populated asynchronously via signals.

**Adaptation:** Each GUI test must use a `TestQueryWorker` — a test-only subclass that
overrides the `moveToThread` pattern by never starting a real thread. All handler slots
execute synchronously in-process when called directly by the test, and result signals
fire immediately. This is required (not optional): `QTest::qWait` is prohibited by
`docs/design/test-strategy.md` and was the subject of fix M-3 in the previous review
cycle.

Pattern:
1. Construct a `TestQueryWorker` (no `QThread`), wire it to the service.
2. Call the service request method (e.g. `m_service->requestSearch(params)`).
3. Because `TestQueryWorker` processes the slot synchronously, the result signal fires
   before the request call returns. Assert model state immediately — no event loop
   draining needed.
4. No `cleanup()` thread teardown required.

The `TestDatabase` opens under `defaultConnection`. The `TestQueryWorker` must open under
`"gui_query_connection"` pointing to the same temporary file. REQ-013 (see §3) specifies
the `TestDatabase::filePath()` accessor that makes this possible.

### 8.3 Test labels and CTest registration

No new test targets are added. The ten existing targets remain. Labels do not change.

### 8.4 `QSignalSpy` on write results

`test_library_service` currently spies on `libraryChanged` to count write operations.
After the change `libraryChanged` is still emitted from `LibraryService` on the GUI
thread; the spy continues to work. Tests that need the new `addBookCompleted` signal
can add a second `QSignalSpy` on that signal.
